# ESP32-S3-N16R8: 아키텍처, 메모리, 실행, 추론 파이프라인

## 0. 요약 카드

**이름 해석**: `ESP32-S3`(칩) `-WROOM-1`(모듈: 칩 + Flash + 안테나) `-N16`(Flash 16 MB) `R8`(PSRAM 8 MB)

| 항목 | 값 |
|---|---|
| CPU | Xtensa LX7 듀얼코어, 240 MHz |
| AI 가속 | PIE (CPU 안의 벡터 확장). NPU 없음 |
| 내부 SRAM | 512 KB ← 가장 빠듯한 자원 |
| PSRAM | 8 MB (Octal SPI, 칩 패키지 내장) |
| Flash | 16 MB |
| 무선 | Wi-Fi, BLE |

## 1. 하드웨어 아키텍처

### 1.1 블록 다이어그램 (단순화)

```
┌──────────────────────────── ESP32-S3R8 칩 ─────────────────────────────┐
│                                                                        │
│   ┌───────────────┐   ┌───────────────┐                                │
│   │ Core 0 (LX7)  │   │ Core 1 (LX7)  │   각 코어: FPU(float32) + PIE   │
│   │  PRO_CPU      │   │  APP_CPU      │   (128비트 벡터 레지스터)         │
│   └───────┬───────┘   └───────┬───────┘                                │
│           └─────────┬─────────┘                                        │
│                     │                                                  │
│   ┌─────────┐  ┌────┴─────────────────────┐  ┌─────────┐               │
│   │ ROM     │  │ 내부 SRAM 512 KB          │  │ RTC     │               │
│   │ 384 KB  │  │  일부는 ICache/DCache로   │  │ SRAM    │               │
│   └─────────┘  │  설정되어 사용됨           │  │ 16 KB   │               │
│                └────┬─────────────────────┘  └─────────┘               │
│                     │ Cache + MMU                                      │
│                ┌────┴─────────┐                                        │
│                │ MSPI (SPI0/1)│  Flash와 PSRAM이 같은 컨트롤러/캐시 공유   │
│                └──┬────────┬──┘                                        │
│                   │        └──────────────┐                            │
│                   │              ┌────────┴────────┐                   │
│                   │              │ PSRAM 8 MB      │ ← 패키지 내장       │
│                   │              │ (Octal SPI)     │                   │
│                   │              └─────────────────┘                   │
│   Wi-Fi / BLE 라디오, GDMA, 주변장치(카메라, I2S, USB ...)                │
└───────────────────┼────────────────────────────────────────────────────┘
                    │
            ┌───────┴────────┐
            │ Flash 16 MB    │ ← 모듈 내부, 칩 외부
            │ (Quad SPI)     │
            └────────────────┘
```

### 1.2 PIE (Processor Instruction Extensions)

- ESP32-S3의 LX7 코어에 Espressif가 추가한 **128비트 벡터 확장**. int8 기준 16개 값을 한 명령어로 처리한다.
- **컴파일러가 자동으로 쓰지 않는다.** ESP-NN, ESP-DL 같은 라이브러리가 어셈블리로 직접 사용한다.
- 그래서 "어떤 라이브러리를 쓰느냐"가 성능을 크게 좌우한다.

### 1.3 듀얼코어

- Core 0 (PRO_CPU), Core 1 (APP_CPU). 대칭형(SMP)으로 FreeRTOS가 두 코어에 태스크를 스케줄링한다.
- ESP-IDF에서는 Wi-Fi/BT 스택 태스크가 기본적으로 Core 0에 배치되는 경향이 있다.
- 태스크를 특정 코어에 고정할 수 있다 (`xTaskCreatePinnedToCore`).

## 2. 메모리 구조와 실행

### 2.1 주소 공간

모든 메모리가 하나의 주소 공간에 매핑돼 있어서, **포인터 주소만 보고도 어느 메모리인지** 알 수 있다.

| 주소 | 메모리 |
|---|---|
| `0x3FCx_xxxx` | 내부 SRAM (데이터: 변수, 스택, 힙) |
| `0x403x_xxxx` | 내부 SRAM (코드: IRAM) |
| `0x3Cxx_xxxx` | 외부 메모리 데이터 (Flash의 상수, PSRAM), 캐시 경유 |
| `0x42xx_xxxx` | 외부 메모리 코드 (Flash XIP), 캐시 경유 |

외부 메모리 영역은 MMU가 Flash 또는 PSRAM의 실제 위치에 매핑한다.

### 2.2 부팅: 펌웨어가 메모리에 놓이는 과정

```
전원 ON
  │
  ▼
① ROM 부트로더 (칩 내부, 수정 불가)
   - 일반 부팅 / 다운로드 모드(펌웨어 굽기) 결정
  │
  ▼
② 2단계 부트로더 (Flash)
   - MMU로 앱의 코드·상수를 주소 공간에 매핑 → 이후 Flash에서 바로 실행(XIP)
   - IRAM 코드와 .data만 내부 SRAM으로 복사
  │
  ▼
③ 앱 시작: 캐시·PSRAM 초기화, FreeRTOS 시작
  │
  ▼
④ app_main()  ← 개발자 코드의 시작점
```

### 2.3 펌웨어 이미지의 위치

| 이미지 안의 부분 | 부팅 후 위치 | 실행/접근 방식 |
|---|---|---|
| 대부분의 코드 (`.flash.text`) | Flash에 그대로 | XIP: `0x42xx_xxxx` 주소로 매핑, ICache 경유 |
| 상수, 모델 가중치 (`.flash.rodata`) | Flash에 그대로 | `0x3Cxx_xxxx` 주소로 매핑, DCache 경유 |
| `IRAM_ATTR` 코드, 인터럽트 핸들러 (`.iram0.text`) | 내부 SRAM으로 복사됨 | 직접 실행 |
| 초기화된 전역 변수 (`.dram0.data`) | 내부 SRAM으로 복사됨 | 직접 접근 |
| `.bss` | 내부 SRAM (0으로 초기화) | 직접 접근 |

### 2.4 SRAM이 실제로 쓰이는 방식

```
내부 SRAM 512 KB
 ├─ ICache          16~32 KB
 ├─ DCache          16~64 KB
 ├─ IRAM 코드       수십 KB    (인터럽트 핸들러, IRAM_ATTR 함수, 일부 IDF/Wi-Fi 코드)
 ├─ .data / .bss    수십 KB    (IDF, 앱의 전역 변수)
 ├─ Wi-Fi/BT 버퍼   수십 KB~   (무선을 쓸 때 동적 할당)
 ├─ 태스크 스택     태스크 수 × 스택 크기
 └─ 남은 힙        ← 앱 + tensor arena가 쓸 공간
```

- 캐시 크기는 설정으로 조절한다. **캐시를 키우면 외부 메모리 접근이 빨라지는 대신 앱이 쓸 수 있는 SRAM이 줄어든다.**
- Wi-Fi를 켜면 앱이 쓸 수 있는 내부 힙은 보통 **200~300 KB 안팎**이다. 설정에 따라 차이가 크다.

### 2.5 캐시: ICache와 DCache

Flash와 PSRAM은 칩 밖에 있어 느리다. CPU는 이들을 직접 읽지 않고 **캐시**(내부 SRAM의 일부)를 거쳐 읽는다. ESP32-S3는 코드용과 데이터용 캐시가 분리되어 있다.

```
                         ┌──────────── CPU ────────────┐
                         │  명령 버스          데이터 버스 │
                         └────┬───────────────────┬────┘
            ┌─────────────────┼───────────────────┼─────────────────┐
 칩 내부     │   ┌─────────┐   │                   │   ┌─────────┐   │
 SRAM 512KB │   │ ICache  │◄──┤                   ├──►│ DCache  │   │
            │   │ 16/32KB │   │                   │   │ 32/64KB │   │
            │   └────┬────┘   │                   │   └────┬────┘   │
            │   IRAM ◄────────┤  (캐시 없이 직접)    ├──► DRAM        │
            │   (코드)         │                   │   (변수, 스택,    │
            │                 │                   │    heap, arena)  │
            └────────┼────────────────────────────────────┼─────────┘
                     │  캐시 미스 시 SPI 버스로 읽어 옴           │
            ┌────────┴────────────────────────────────────┴─────────┐
 칩 외부     │  Flash 16MB: 코드(.text), 상수(.rodata, 모델 가중치)      │
            │  PSRAM 8MB : (켜면) 큰 데이터                            │
            └───────────────────────────────────────────────────────┘
```

| 대상 | 저장 위치 | 접근 경로 |
|---|---|---|
| 대부분의 코드 (`.flash.text`) | Flash | **ICache** |
| 상수, 모델 가중치 (`.flash.rodata`) | Flash | **DCache** |
| PSRAM에 둔 데이터 | PSRAM | **DCache** |
| `IRAM_ATTR` 코드, 인터럽트 핸들러 | 내부 SRAM (IRAM) | 직접 실행 (캐시 없음) |
| 전역 변수, 스택, 힙, 내부 SRAM의 tensor arena | 내부 SRAM (DRAM) | 직접 접근 (캐시 없음) |

#### 캐시와 IRAM/DRAM은 같은 SRAM을 나눠 쓴다

- **IRAM**: 명령 버스로 접근하는 내부 SRAM. 코드를 캐시 없이 직접 실행한다.
- **DRAM**: 데이터 버스로 접근하는 내부 SRAM. 변수, 스택, 힙이 놓인다.

## 3. 개발 환경

### 3.1 프레임워크 비교

모든 선택지가 ESP-IDF 위에 있다. 차이는 "개발자가 무엇을 기준으로 코드를 쓰느냐"다.

```
 Python 스크립트       Arduino 스케치           ESP-IDF 앱 (C/C++)
       │                   │                       │
 MicroPython 인터프리터  Arduino-ESP32 (API 래퍼)     │
       └───────────────────┴───────────┬───────────┘
                                    ESP-IDF  (FreeRTOS, 드라이버, 힙)
```

| 옵션 | 성격 | ML 관점 |
|---|---|---|
| **ESP-IDF** | 기반 SDK. 칩 기능을 전부 사용 | ESP-DL, esp-tflite-micro가 **ESP-IDF 컴포넌트로 배포됨** |
| **Arduino-ESP32** | ESP-IDF 위의 API 래퍼. 쉬움 | 미리 빌드된 ESP-IDF를 써서 설정 변경과 컴포넌트 추가가 어려움. TFLM은 커뮤니티 포팅판 사용 |
| **MicroPython** | ESP-IDF로 만든 Python 인터프리터 | 고성능 추론에는 부적합 |

- 추론 런타임은 프레임워크 위에서 동작하도록 만들어지므로, 어떤 프레임워크를 고르느냐에 따라 쓸 수 있는 런타임이 달라진다.
-   ML 추론을 본격적으로 하려면 **ESP-IDF를 직접 쓰는 것이 가장 제약이 적다.**

> **Tip: N16R8에서 처음 바꿔야 할 설정** (기본값 그대로면 자원을 제대로 못 씀)
> - Flash 크기 16 MB (기본 2 MB)
> - PSRAM 활성화 + Octal 모드 (기본 꺼짐)
> - CPU 240 MHz (기본 160 MHz)
> - 필요하면 캐시 확대: ICache 32 KB / DCache 64 KB (기본 16 KB / 32 KB)

### 3.2 추론 엔진

#### 선택지 요약

| 엔진 | 성격 | 입력 포맷 |  ESP32-S3 벡터 확장(PIE) | 비고 |
|---|---|---|---|---|
| **esp-tflite-micro** | TFLM의 Espressif 포팅 | `.tflite` | ESP-NN 커널 자동 사용 | 자료가 가장 많음, 무난한 출발점 |
| **ESP-DL** | Espressif 전용 | ONNX → `.espdl` | PIE 어셈블리 커널 | S3에서 가장 빠른 편, PyTorch 경로에 자연스러움 |
| **Edge Impulse** | 통합 플랫폼 | 플랫폼 내부 | 내부적으로 ESP-NN 사용 | 빠른 프로토타입 |
| ESP-WHO / ESP-SR | 응용 프레임워크 | 사전 학습 모델 | ESP-DL 기반 | 얼굴 감지/인식, wake word, 음성명령 |

#### esp-tflite-micro (TFLM + ESP-NN)

**구조**:

```
앱 코드
  │ TFLM API (MicroInterpreter, MicroMutableOpResolver)
  ▼
TFLM 런타임 (인터프리터, memory planner)
  │ 커널 호출
  ▼
ESP-NN (S3용 PIE 최적화 커널)  ← Conv, DepthwiseConv, FC, Pooling 등
  │ 지원하지 않는 op는
  ▼
TFLM 기본 C 커널 (reference, 느림)
```

- ESP-NN은 기본으로 켜져 있다. menuconfig의 "ESP TFLite-Micro → Use ESP-NN optimized kernels"에서 끌 수 있다.
- 효과 예시 (esp-tflite-micro README, S3 person detection): ESP-NN 없이 약 **2300 ms → ESP-NN 사용 시 약 54 ms**. 같은 TFLM이라도 커널 라이브러리가 성능을 결정한다는 좋은 예다.

**모델 변환 경로**:

```
TF/Keras 모델 → TFLiteConverter (int8 PTQ, representative_dataset) → model.tflite
  → xxd -i model.tflite > model_data.cc  (C 배열로 변환, Flash에 들어감)
```

**사용 코드 골격** (arena 할당 → 텐서 배치 → 추론):

```cpp
extern const unsigned char g_model[];          // Flash (.rodata)
constexpr int kArenaSize = 150 * 1024;

void setup_model() {
    const tflite::Model *model = tflite::GetModel(g_model);
    static tflite::MicroMutableOpResolver<5> resolver;   // 쓰는 op만 등록 (생략)

    // arena 위치는 개발자가 정함: 내부 SRAM 시도 → 실패하면 PSRAM
    uint8_t *arena = (uint8_t *)heap_caps_malloc(kArenaSize, MALLOC_CAP_INTERNAL);
    if (!arena) arena = (uint8_t *)heap_caps_malloc(kArenaSize, MALLOC_CAP_SPIRAM);

    static tflite::MicroInterpreter interpreter(model, resolver, arena, kArenaSize);
    interpreter.AllocateTensors();   // arena 안에 텐서 배치
    interpreter.Invoke();            // 추론
}
```

#### ESP-DL

**구조와 변환 경로**:

```
PyTorch / TF 모델
  → ONNX로 export (ESP-PPQ는 PyTorch API도 제공)
  → ESP-PPQ (Python 양자화 도구: int8/int16, calibration 데이터)
  → model.espdl (FlatBuffers 포맷)
  → Flash (rodata 임베드 또는 파티션) / SD 카드
  → ESP-DL 런타임 (C++) + PIE 최적화 커널
```

- 최적화 대상은 **ESP32-S3와 ESP32-P4**. 다른 ESP 칩(ESP32, C 시리즈, S2 등)도 컴포넌트 목록에는 있지만 최적화 수준이 다르다.

**사용 코드 골격** (v3.3 기준, 버전에 따라 API가 다를 수 있음):

```cpp
#include "dl_model_base.hpp"

// 주요 인자:
//   location   : 모델 위치 (FLASH_RODATA / FLASH_PARTITION / SDCARD)
//   param_copy : 가중치를 Flash에서 PSRAM으로 복사할지 (기본 true → 속도↑, PSRAM 사용↑)
dl::Model *model = new dl::Model("model", fbs::MODEL_LOCATION_IN_FLASH_RODATA);

model->run(input_tensor);
auto outputs = model->get_outputs();
```

**TFLM과의 차이**:
- 메모리를 개발자가 arena로 넘겨주는 대신, **런타임이 내부 메모리 매니저로 할당**한다.
- int16 양자화를 지원해서 int8로 정확도가 부족한 모델에 대안이 된다.
- 지원 op와 API가 버전마다 바뀌는 편이라 GitHub의 해당 버전 문서를 기준으로 봐야 한다.

#### 어떤 걸 고를까

- **처음 배우거나 TF/Keras로 학습**했다면 esp-tflite-micro.
- **PyTorch로 학습**했거나 **S3에서 성능을 최대로** 내려면 ESP-DL.
- **데이터 수집부터 빠르게** 하려면 Edge Impulse.
- **얼굴 인식, wake word 같은 완성 기능**이 필요하면 ESP-WHO / ESP-SR.

흔한 흐름: **TFLM으로 먼저 돌려 기준점을 잡고 → 성능이 부족하면 ESP-DL로 옮겨 비교.**

## 4. 메모리 배치 제어

### 4.1 빌드 시 배치 (속성 매크로)

| 매크로 / 방법 | 효과 |
|---|---|
| (기본) 함수 | Flash (XIP) |
| `IRAM_ATTR` | 함수를 내부 SRAM(IRAM)에 배치 |
| `const` 전역 배열 | Flash `.rodata` |
| `DRAM_ATTR` | 상수/데이터를 내부 SRAM에 강제 배치 |
| (기본) 전역 변수 | 내부 SRAM (`.data`/`.bss`) |
| `EXT_RAM_BSS_ATTR` | 초기값 없는 전역 변수를 PSRAM에 배치 (`CONFIG_SPIRAM_ALLOW_BSS_SEG_EXTERNAL_MEMORY` 필요) |

```c
const int8_t g_model[] = {...};                 // Flash
static int8_t g_input[96 * 96];                 // 내부 SRAM (.bss)
EXT_RAM_BSS_ATTR static uint8_t g_frame[320 * 240 * 2];  // PSRAM

void IRAM_ATTR gpio_isr(void *arg) { ... }      // 내부 SRAM에서 실행
```

### 4.2 실행 중 할당 (heap_caps API)

ESP-IDF의 힙은 메모리 종류별 **capability**로 구분된다. 할당할 때 어느 메모리에 둘지 지정한다.

```c
#include "esp_heap_caps.h"

uint8_t *arena = heap_caps_malloc(200 * 1024, MALLOC_CAP_INTERNAL);    // 내부 SRAM (빠름)
uint8_t *frame = heap_caps_malloc(320 * 240 * 2, MALLOC_CAP_SPIRAM);   // PSRAM (크지만 느림)
```

### 4.3 일반 malloc의 기본 정책

`CONFIG_SPIRAM_USE_MALLOC`을 켜면 일반 `malloc`도 PSRAM을 쓴다.

- 작은 할당(기본 16 KB 미만)은 내부 SRAM, 큰 할당은 PSRAM으로 간다. **할당 순간 한 번 정해지고 이후 옮겨지지 않는다.**
- 추론용 큰 버퍼는 일반 `malloc`에 맡기지 말고 `heap_caps_malloc`으로 **명시적으로 위치를 정하는 것**이 좋다.
