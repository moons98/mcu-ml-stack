# MCU 기초: 생태계, 펌웨어, 메모리, 추론 엔진

> MCU 위에서 ML 추론을 돌리기 위해 알아야 할 **벤더 중립적인 공통 개념**을 정리한 노트.

---

## 0. 용어집

| 용어 | 뜻 |
|---|---|
| **MCU** | Microcontroller Unit. CPU, 메모리, 주변장치가 칩 하나에 들어간 소형 컴퓨터 |
| **ISA** | Instruction Set Architecture. CPU가 이해하는 명령어 체계 (Arm, RISC-V, Xtensa 등) |
| **PSRAM** | Pseudo-SRAM. 외부(또는 패키지 내부)에 붙는 큰 용량의 휘발성 메모리. 내부 SRAM보다 느림 |
| **TCM** | Tightly Coupled Memory. 캐시를 거치지 않고 코어에 직결된 고속 SRAM (Cortex-M7 등) |
| **XIP** | Execute-In-Place. 코드를 RAM에 복사하지 않고 Flash에서 바로 실행 |
| **캐시** | 느린 외부 메모리(Flash, PSRAM)에서 자주 쓰는 부분을 SRAM에 임시 보관 |
| **펌웨어** | MCU의 Flash에 저장되어 실행되는 프로그램 바이너리 (앱 + RTOS + 드라이버 + 라이브러리) |
| **RTOS** | Real-Time OS. 태스크 스케줄링 정도만 제공하는 경량 OS (FreeRTOS, Zephyr 등) |
| **Tensor arena** | 추론 엔진이 activation 등 중간 텐서를 배치하는 하나의 큰 메모리 버퍼 |

## 1. MCU란 무엇인가

### 1.1 MCU vs MPU/SoC vs PC

| | MCU | MPU / 애플리케이션 SoC | PC / 서버 |
|---|---|---|---|
| 예시 | ESP32, STM32, nRF52 | 라즈베리파이 4/5, Jetson, 스마트폰 AP | x86 데스크톱 |
| 클럭 | 수십 MHz ~ 수백 MHz | 1~3 GHz | 3~5 GHz |
| RAM | **수백 KB** (+ 선택적 PSRAM 수 MB) | 수 GB (외부 DRAM) | 수십 GB |
| 저장소 | 내장/외장 Flash 수 MB | eMMC, SD 카드 수십 GB | SSD |
| OS | 없음 (bare-metal) 또는 RTOS | Linux, Android | Windows, Linux |
| 가상 메모리 | **없음** | 있음 | 있음 |
| 프로그램 실행 | 하나의 펌웨어가 전원 ON부터 끝까지 실행 | OS가 여러 프로세스를 로드/실행 | 동일 |
| 전력 | µW ~ 수백 mW | 수 W | 수십~수백 W |
| ML 런타임 | TFLM, 벤더 전용 엔진 | TFLite, ONNX Runtime, TensorRT | PyTorch 등 |

### 1.2 MCU 세계의 핵심 제약

- **OS가 없거나 아주 얇다.** 프로세스, 동적 라이브러리 로더, 가상메모리가 없다.
- **메모리가 KB 단위다.** 특히 SRAM이 가장 빠듯한 자원이다.
- **프로그램은 빌드 시점에 하나의 바이너리로 확정된다.** 실행 중에 새 프로그램을 설치해서 실행하는 개념이 없다.
- **메모리 배치를 개발자가 직접 신경 써야 한다.** 어떤 데이터가 어느 메모리에 놓이는지가 성능을 직접 좌우한다.

## 2. MCU 생태계

### 2.1 코어 IP 회사와 칩 제조사

왼쪽은 CPU 코어(설계), 오른쪽은 그 코어로 칩을 만들어 파는 회사다. Arm은 칩을 팔지 않고 설계만 라이선스한다.

```
[코어 아키텍처(ISA) / IP]               [칩 제조사: 코어 + 메모리 + 주변장치 + 무선 → MCU 완제품]
  Arm (Cortex-M)            ──라이선스──▶  ST, NXP, Nordic, Renesas, Infineon, Raspberry Pi, Microchip ...
  RISC-V (오픈 ISA)          ──자유 사용──▶  Espressif(C/H/P 시리즈), WCH, GigaDevice, Raspberry Pi ...
  Cadence Tensilica Xtensa  ──라이선스──▶  Espressif(ESP32, ESP32-S2/S3)
  벤더 자체 ISA              ──자체 설계──▶  Microchip(AVR, PIC), TI(MSP430), Renesas(RX), 8051 계열 ...
```

| ISA | 위상 |
|---|---|
| **Arm Cortex-M** | 32비트 MCU의 대다수. 사실상 표준 |
| **RISC-V** | 라이선스료 없는 오픈 ISA. 신규 칩에서 빠르게 증가 |
| **Xtensa** | Cadence의 IP. Espressif ESP32, S2, S3에서 사용 |
| 벤더 자체 ISA | Microchip AVR/PIC, TI MSP430, Renesas RX, 8051 계열 등. 오래된 라인이나 특정 분야에 남아 있음 |

- 같은 Cortex-M4 코어로 만든 칩이 ST, NXP, Nordic 등에서 각각 나온다. 
  - 코어가 같으면 명령어가 같으므로 **컴파일러와 최적화 라이브러리(CMSIS-NN 등)를 공유**할 수 있다.
- **RISC-V는 ISA(명세)만 공개돼 있다.** 실제 코어는 SiFive, Andes 같은 IP 회사에서 사 오기도 하고, 칩 회사가 직접 설계하기도 한다 (Espressif의 RISC-V 칩은 자체 설계 코어).
- **벤더 자체 ISA**를 쓰는 회사는 코어 설계와 칩 제조를 모두 직접 한다.
- ML 추론 관점에서는 Arm, RISC-V, Xtensa가 주로 의미 있다. 자체 ISA 라인은 대부분 8/16비트이거나 ML 생태계가 거의 없다.

### 2.2 Arm Cortex-M 계열

산업계의 사실상 표준이다. 숫자가 높을수록 대체로 고성능이다.

| 코어 | 특징 | ML 관련 확장 | 대표 칩 |
|---|---|---|---|
| Cortex-M0 / M0+ | 초저전력, 단순한 구조 | 없음 | RP2040, STM32G0 |
| Cortex-M3 | 범용 | 없음 | STM32F1 (구형) |
| Cortex-M4 | FPU(선택) | DSP 확장 | STM32F4, nRF52840 |
| Cortex-M7 | 고성능, 캐시, TCM | DSP 확장 | STM32F7/H7, NXP i.MX RT |
| Cortex-M33 | M4급 + 보안(TrustZone) | DSP 확장 | nRF5340, RP2350, STM32U5 |
| **Cortex-M55 / M85** | ML/DSP 성능 강화 | Helium (벡터 확장) | STM32N6, Renesas RA8, Alif Ensemble |

### 2.3 주요 칩 제조사

| 회사 | 대표 제품군 | 코어 | 강점 | 주 사용처 |
|---|---|---|---|---|
| **ST** | STM32 | Cortex-M 전 라인업 | 라인업이 가장 넓고 툴(CubeIDE, CubeMX)과 문서가 풍부 | 산업계, 제품 개발의 표준 |
| **Espressif** | ESP32 시리즈 | Xtensa → RISC-V로 전환 중 | 저렴한 가격에 Wi-Fi/BLE 내장 | IoT, 취미, 프로토타입 |
| **Nordic** | nRF52/53/54 | Cortex-M (+RISC-V) | BLE 저전력 최강 | 웨어러블, BLE 기기 |
| **NXP** | i.MX RT, LPC, MCX | Cortex-M | 고성능 크로스오버 MCU, 자동차 | 산업, 자동차 |
| **Raspberry Pi** | RP2040, RP2350 | Cortex-M0+/M33 (+RISC-V) | 저렴, 문서가 좋음 | 교육, 취미 |
| **Renesas** | RA, RX | Cortex-M, 자체 코어 | 산업, 자동차 | 산업 |
| **Infineon** | PSoC, XMC | Cortex-M | 전력, 자동차, 보안 | 산업 |
| **Microchip** | SAM, PIC, AVR | Cortex-M, 자체 코어 | 오래된 8비트 생태계 | 산업, 구형 Arduino |

TinyML 학습/연구용으로 자주 쓰이는 보드:
- Arduino Nano 33 BLE Sense (nRF52840): TinyML 교재의 고전
- STM32 Nucleo / Discovery 보드
- ESP32-S3 개발 보드
- OpenMV (STM32H7 기반 비전 보드)

### 2.4 AI 가속 수단

MCU의 ML 가속은 아래 단계로 발전해 왔다.

```
                                 ┌──────────────────────────────────────┐
 Level 3  NPU                    │ CPU 밖의 별도 가속기                   │  STM32N6, Alif, NXP MCX N
                                 └──────────────────────────────────────┘
 ─────────────────────────── CPU 경계 ───────────────────────────────────
 Level 2  벡터 확장               CPU 안의 전용 벡터 장치                    Cortex-M55/M85 (Helium), ESP32-S3 (PIE)
 Level 1  DSP 확장                32비트 레지스터를 쪼개 여러 값을 동시 처리   Cortex-M4/M7/M33
 Level 0  확장 없음               일반 명령어로 하나씩 계산                   Cortex-M0/M0+
```

| 단계 | 대표 | 하는 일 | 누가 활용하나 |
|---|---|---|---|
| 0. 없음 | Cortex-M0/M0+ | 일반 정수 명령어로 하나씩 계산 | 컴파일러 |
| 1. DSP 확장 | Cortex-M4/M7/M33 | 32비트 레지스터를 쪼개 int16 2개씩 처리하는 정도 | 커널 라이브러리 (CMSIS-NN) |
| 2. 벡터 확장 | Helium (Cortex-M55/M85), PIE (ESP32-S3), RISC-V V 확장 | CPU 안의 전용 벡터 장치로 여러 값을 한 번에 처리. Level 1 대비 ML 성능이 수 배 | 커널 라이브러리 (CMSIS-NN, ESP-NN, ESP-DL) |
| 3. NPU | ST Neural-ART (STM32N6), Arm Ethos-U55 (Alif, Infineon PSoC Edge), NXP eIQ Neutron (MCX N), MAX78000 CNN 가속기 | 신경망 연산 전용 하드웨어. CPU 대비 수십 배 빨라질 수 있음 | **NPU 전용 컴파일러** (벤더 툴, Vela 등) |

> 확장이 있어도 컴파일러가 자동으로 잘 쓰지 못하는 경우가 많다. 실제 효과는 CMSIS-NN, ESP-NN 같은 **커널 라이브러리가 그 명령어를 쓰느냐**에 달려 있다.

## 3. 개발 환경과 펌웨어

### 3.1 개발 환경

MCU 개발에는 코드 작성부터 실행까지 단계마다 도구가 필요하다.

| 단계 | 필요한 것 |
|---|---|
| 코드 작성 | SDK(칩 주변장치를 다루는 라이브러리), RTOS |
| 빌드 | 크로스 컴파일러 (PC에서 MCU용 기계어 생성), 빌드 시스템 |
| 굽기 | 플래시 도구 (USB로 MCU의 Flash에 기록) |
| 확인 | 시리얼 로그, 디버거 |

- 이 도구들은 프레임워크 하나를 고르면 전부 묶여서 설치된다.
- 그래서 실제로 정하는 것은 "어떤 프레임워크를 쓸지"다.

**프레임워크 선택지** (위로 갈수록 쉽고, 아래로 갈수록 칩 기능을 세밀하게 제어할 수 있다):

```
쉬움   Arduino / MicroPython             ← 빠른 프로토타이핑. 내부적으로 벤더 SDK 위에서 동작
  │
세밀   벤더 SDK (ESP-IDF, STM32Cube 등)   ← 칩 기능을 전부 사용. ML 추론은 보통 여기서
```

### 3.2 펌웨어 빌드 흐름

```
[PC]
 앱 코드 + RTOS/SDK + 추론 라이브러리 + 모델 데이터
   │ ① 크로스 컴파일: 소스 → 오브젝트 파일(.o), 라이브러리(.a)
   ▼
 .o / .a 파일들
   │ ② 링크: 링커 스크립트에 따라 모든 코드/데이터를 메모리 주소에 배치하고 하나로 합침
   ▼
 firmware.elf   (디버그 심볼 포함)
   │ ③ 변환: 실제로 굽는 이미지만 추출
   ▼
 firmware.bin
   │ ④ 플래시: USB/UART/JTAG로 전송해 Flash 칩에 기록 ("굽는다")
   ▼
[MCU Flash]
   │ ⑤ 전원 ON → 부트 ROM → (부트로더) → 앱 진입점 실행
```

### 3.3 정적 링크

- **정적 링크**: 사용하는 라이브러리 코드를 빌드 시점에 실행 파일 안으로 **통째로 복사해 넣는 것**.
- **동적 링크**: 실행할 때 OS가 `.so` / `.dll`을 찾아서 불러오는 것 (PC 방식).
- MCU에는 실행 중에 라이브러리를 불러올 OS 로더가 없으므로 **사실상 모든 것이 정적 링크**된다.
- 결과적으로 앱, RTOS, 드라이버, 무선 스택, 추론 런타임, (경우에 따라) 모델까지 **하나의 바이너리**가 된다.

### 3.4 Flash 파티션과 업데이트

Flash는 보통 **파티션 테이블**로 영역을 나눈다.

```
| 부트로더 | 파티션 테이블 | 설정 저장소(NVS 등) | 앱 (펌웨어) | 앱 2 (OTA용) | 데이터 (모델, 파일시스템) |
```

- **모델을 별도 파티션에 두면** 앱을 다시 빌드하지 않고 모델만 교체할 수 있다.
- **OTA (Over-The-Air)**: 무선으로 새 펌웨어를 받아 두 번째 앱 파티션에 쓰고, 재부팅 시 전환한다.

## 4. 코드 실행과 메모리 구조

### 4.1 메모리 종류

| 메모리 | 휘발성 | 속도 | 용량 (일반적) | 주 용도 |
|---|---|---|---|---|
| 레지스터 | O | 최고 | 수십 개 | 연산 피연산자 |
| TCM | O | 매우 빠름 (캐시 불필요) | 수십~수백 KB | 핵심 코드/데이터 (Cortex-M7 등) |
| 내부 SRAM | O | 빠름 | 수십 KB ~ 1 MB | 스택, 힙, 전역 변수, 캐시, activation |
| 외부 PSRAM / SDRAM | O | 느림 (캐시 경유) | 수 MB ~ 수십 MB | 큰 버퍼 (카메라 이미지 등), SRAM에 안 들어가는 activation |
| 내장/외장 Flash | X | 읽기 느림 (캐시 경유), 쓰기 매우 느림 | 수백 KB ~ 수십 MB | 코드, 상수, 모델 가중치 |

### 4.2 XIP와 캐시

**"프로그램을 RAM에 올려서 실행한다"는 PC의 방식과 다르다.** 대부분의 MCU는 XIP 방식이다.

```
            CPU (연산은 항상 레지스터에서)
               │
     ┌─────────┴─────────────┐
     │                       │
  내부 SRAM               캐시 (SRAM 일부를 사용)
  (직접 접근)                 │ 캐시 미스 시 버스로 가져옴
                    ┌────────┴────────┐
                 Flash             PSRAM
              (코드, 상수)        (큰 데이터)
```

1. MMU(또는 메모리 컨트롤러)가 Flash와 PSRAM을 **CPU 주소 공간에 매핑**한다.
2. CPU는 해당 주소를 일반 메모리처럼 읽는다.
3. 캐시에 있으면 바로 쓰고(히트), 없으면 외부 버스로 가져와 캐시에 채운다(미스).

그래서:
- 코드는 Flash에 그대로 있다. 실행할 때 필요한 부분만 캐시(SRAM 일부)에 잠깐 복사됐다가 밀려난다.
  - 캐시는 고정 크기라서, 코드가 커져도 앱이 쓸 SRAM은 줄지 않는다.
- 모델 가중치처럼 큰 `const` 데이터도 Flash에 둔 채로 읽을 수 있어 **SRAM을 차지하지 않는다.**
- 인터럽트 핸들러처럼 캐시 미스로 지연되면 안 되거나 Flash를 쓸 수 없는 순간에도 실행돼야 하는 코드는 **내부 SRAM(또는 TCM)에 따로 배치**한다.
- PSRAM도 주소 공간에 매핑돼 있어 **포인터로 바로 읽고 쓴다.** 
  - 코드상으로는 내부 SRAM과 구분되지 않는다.
  - 데이터는 PSRAM에 있고, CPU가 캐시를 거쳐 레지스터로 가져와 계산한다.

### 4.3 링커 섹션: 무엇이 어디에 놓이나

| 섹션 | 내용 | 위치 |
|---|---|---|
| `.text` | 실행 코드 | Flash (XIP), 일부는 내부 SRAM |
| `.rodata` | 상수, 문자열, `const` 배열 (모델 가중치 포함) | Flash |
| `.data` | 초기값이 있는 전역 변수 | 초기값은 Flash에 있고, 부팅 시 SRAM으로 복사됨 |
| `.bss` | 초기값 없는 전역 변수 (0으로 초기화) | SRAM |
| heap | `malloc` / `new`로 할당 | SRAM (+ 설정에 따라 PSRAM) |
| stack | 함수 지역 변수, 호출 정보. **태스크마다 하나씩** | SRAM |

```c
const int8_t model_weights[] = {...};  // .rodata → Flash (SRAM 사용 안 함)
int8_t input_buf[1024];                // .bss    → SRAM
int counter = 5;                       // .data   → SRAM (초기값은 Flash에서 복사)

void f(void) {
    int8_t tmp[256];                   // stack   → 현재 태스크의 스택 (SRAM)
    uint8_t *p = malloc(100 * 1024);   // heap    → 설정에 따라 SRAM 또는 PSRAM
}
```

### 4.4 배치를 정하는 시점과 주체

| 시점 | 주체 | 결정되는 것 | 방법 |
|---|---|---|---|
| 빌드 시 | 개발자 + **링커** | 코드, 상수, 전역 변수의 위치 | 링커 스크립트, 섹션 속성 매크로 |
| 실행 중 할당 시 | **개발자 코드** | 동적 버퍼의 위치 | 메모리 종류를 지정하는 할당 API |
| 실행 중 할당 시 | **SDK 힙 정책** | 지정하지 않은 `malloc`의 위치 | SDK 설정 (예: 일정 크기 이상은 PSRAM) |
| 추론 시 | **추론 엔진** | arena 안의 텐서 오프셋 | 엔진이 자동으로 배치 |
| 매 접근마다 | **하드웨어 캐시** | 캐시에 무엇이 있는지 | 자동 |

### 4.5 SRAM이 가장 빠듯한 이유

내부 SRAM은 앱이 혼자 쓰는 공간이 아니다. 아래 항목들이 먼저 자리를 차지하고, 남은 공간을 앱이 쓴다.

```
내부 SRAM 전체
 ├─ 캐시 (외부 메모리를 쓰려면 필수)
 ├─ 내부 SRAM에서 실행해야 하는 코드 (인터럽트 핸들러 등)
 ├─ RTOS 커널, 드라이버, 무선 스택 버퍼 (Wi-Fi/BLE를 쓰면 상당히 큼)
 ├─ 각 태스크의 스택
 ├─ 전역 변수 (.data, .bss)
 └─ 남은 것 = 앱이 쓸 수 있는 힙   ← 여기서 tensor arena를 할당해야 함
```

### 4.6 정적 할당 선호

MCU 펌웨어는 동적 할당(`malloc`)을 최소화하는 경향이 있다.
- 힙 **단편화**: 오래 실행하면 빈 공간이 쪼개져서 큰 블록을 할당할 수 없게 된다.
- **결정성**: 할당 실패가 실행 중에 갑자기 일어나면 대응하기 어렵다.
- 그래서 추론 엔진도 보통 **시작할 때 큰 arena 하나를 할당**하고 그 안에서 스스로 관리한다.

## 5. MCU 추론 엔진

### 5.1 추론 스택의 3층 구조

```
펌웨어 (하나의 바이너리)
┌──────────────────────────────────────────────┐
│ 앱 코드             전처리, 후처리, 결과 전송      │
├──────────────────────────────────────────────┤
│ 추론 런타임         TFLM, ESP-DL                │ ← 모델을 "어떤 순서로" 실행할지
│ 커널 라이브러리      CMSIS-NN, ESP-NN            │ ← 연산 하나를 "어떻게" 계산할지
├──────────────────────────────────────────────┤
│ 프레임워크 / SDK     ESP-IDF, STM32Cube 등       │ ← 칩과 시스템 전체를 관리
└──────────────────────────────────────────────┘
```

| 층 | 하는 일 | PC/GPU에 대응하면 |
|---|---|---|
| 프레임워크 / SDK | RTOS 태스크, 드라이버, 메모리 할당, 부팅. 빌드 도구도 포함 | OS + 드라이버 |
| 추론 런타임 | 모델 해석 → arena 안에 텐서 배치 → op 순서대로 커널 호출 | ONNX Runtime, PyTorch 실행 엔진 |
| 커널 라이브러리 | Conv2D 같은 연산 하나를 하드웨어 명령어(DSP, PIE 등)로 계산 | cuDNN, MKL |

- 런타임이 관리하는 자원은 **모델용 메모리(arena)뿐**이다. 태스크나 전체 힙 같은 시스템 자원은 프레임워크가 관리한다.
- 여기서 "커널"은 연산 함수를 뜻한다. RTOS의 "OS 커널"과는 다른 말이다.

### 5.2 실행 방식

| 방식 | 동작 | 예시 | 장단점 |
|---|---|---|---|
| **인터프리터** | 런타임(코드)이 모델 파일(데이터)을 읽고, op 순서대로 커널 함수를 호출 | TFLM, ESP-DL | 모델만 바꿔 끼우기 쉬움 / 런타임 코드 크기와 약간의 오버헤드 |
| **AOT 컴파일** | 모델을 빌드 시점에 C 코드로 변환. 인터프리터 없음 | Edge Impulse EON, ST Edge AI, (구) microTVM | 작고 빠름 / 모델이 바뀌면 재빌드 |

어느 방식이든 **런타임(또는 생성된 코드)은 펌웨어에 정적 링크**된다.

### 5.3 엔진 계층 구조

```
                    모델 포맷 (공통): .tflite / ONNX
                               │
      ┌────────────────────────┼─────────────────────────────┐
      ▼                        ▼                             ▼
 범용 런타임              크로스플랫폼 도구                  벤더 전용 툴
 TFLM                    Edge Impulse                    ST Edge AI (STM32Cube.AI)
                         ExecuTorch                      NXP eIQ
                                                         Espressif ESP-DL
                                                         Renesas, Infineon 툴
      │                        │                             │
      └────────────────────────┴─────────────┬───────────────┘
                                             ▼
                        아키텍처별 최적화 커널 / 컴파일러
                        ├ CMSIS-NN         → Arm Cortex-M (DSP, Helium)
                        ├ ESP-NN           → ESP32 (PIE)
                        ├ Ethos-U + Vela   → Arm NPU
                        └ 벤더 NPU 컴파일러 → ST Neural-ART, NXP Neutron 등
```

### 5.4 주요 엔진

| 분류 | 엔진 | 입력 | 핵심 |
|---|---|---|---|
| 범용 런타임 | **TFLM** | `.tflite` | 사실상 표준. 어떤 MCU에서도 돌고, 칩별 최적화 커널이 붙음 |
| 크로스플랫폼 | **Edge Impulse** | 자체 플랫폼 | 데이터 수집부터 배포까지 웹에서 한 번에 |
| | **ExecuTorch** | PyTorch | PyTorch 진영 런타임. MCU 지원은 아직 성장 중 |
| 벤더 전용 | **ST Edge AI** | `.tflite`, ONNX | STM32 전용, NPU 지원 |
| | **NXP eIQ** | `.tflite` | NXP 전용, NPU 지원 |
| | **ESP-DL** | ONNX | ESP32-S3/P4 전용 |

- TFLM의 현재 공식 명칭은 *LiteRT for Microcontrollers*다.
- microTVM은 개발이 중단되었다.

### 5.5 선택 가이드

- **NPU가 달린 칩**이면 벤더 툴이 사실상 필수다. NPU 컴파일러가 벤더 툴에 있기 때문이다.
- **성능을 최대로** 끌어내야 하면 벤더 툴이 유리하다.
- **여러 칩을 비교하거나 이식성**이 중요하면 TFLM. 어디서나 돌고 칩별 커널이 자동으로 붙는다.
- **빠르게 프로토타입**을 만들려면 Edge Impulse. 데이터 수집부터 배포까지 한 번에 된다.

## 6. 성능 지표

| 지표 | 의미 | 비고 |
|---|---|---|
| **Latency** | 추론 1회 소요 시간 | 전처리/후처리 포함 여부를 명시할 것 |
| **Peak RAM** | arena + 입력/출력 버퍼 + 스택 | 내부 SRAM과 외부 메모리를 구분해 기록 |
| **Flash footprint** | 런타임 코드 + 모델 크기 | |
| **에너지** | 추론 1회당 소비 에너지 (mJ) | 배터리 기기에서 중요 |
| **정확도** | 양자화 후 정확도 | float 모델 대비 하락폭 |

**MLPerf Tiny**: MCU급 기기의 ML 성능을 비교하는 표준 벤치마크. 4개 태스크(키워드 인식, 시각적 wake word, 이미지 분류, 이상 탐지)로 latency와 에너지를 측정한다.
